Build the complete backend and database for Hidden Nepal, a community-driven travel discovery platform for Nepal with four roles: viewer, contributor, moderator, admin. The frontend is React + Vite + TypeScript and currently uses a Zustand mock store; replace it with real API calls. Use PostgreSQL 15+ as the database and a real authentication system (JWT-based, email/password + Google OAuth, with password reset and email verification). Deliver migrations, seed data, REST/RPC endpoints, storage, RLS-style authorization, tests, and updated frontend hooks.

1. Tech stack
Database: PostgreSQL 15+ (with pgcrypto, uuid-ossp, pg_trgm, unaccent, citext).
Backend runtime: Node.js 20 + TypeScript, framework of your choice (Fastify, NestJS, or Express + zod). Keep it modular: routes/, services/, repositories/, schemas/, middleware/, jobs/.
ORM / query layer: Drizzle ORM or Kysely (typed, migration-friendly). No raw string SQL from request handlers.
Auth: JWT access tokens (15 min) + rotating refresh tokens (httpOnly, Secure, SameSite=Lax, 30 days). Argon2id password hashing. Google OAuth 2.0. Magic-link optional.
Storage: S3-compatible object storage (AWS S3 / Cloudflare R2 / MinIO). Signed upload URLs.
Email: SMTP via Nodemailer or a transactional provider (Resend / Postmark / SES). HTML templates for verification, reset, moderation notifications.
Background jobs: BullMQ + Redis for emails, image processing, view-count flushing, audit log fan-out.
Validation: zod schemas shared between client and server.
API style: REST with JSON; OpenAPI 3.1 spec auto-generated.
Tests: Vitest + Supertest; testcontainers for Postgres.
Tooling: Docker Compose for local Postgres + Redis + MinIO + Mailhog.
2. Database schema
Conventions for every table: id uuid primary key default gen_random_uuid(), created_at timestamptz not null default now(), updated_at timestamptz not null default now() maintained by a shared set_updated_at() trigger. Foreign keys cascade where it makes sense; otherwise restrict.

3. Authorization model
Implement an authorization layer in the API (middleware) that derives the caller's roles from user_roles and enforces these rules. Mirror the same checks at the database layer using Postgres RLS so the model holds even if a query slips through.

Helper SQL:

create or replace function public.has_role(_uid uuid, _role app_role)
returns boolean language sql stable security definer set search_path = public as $$
  select exists(select 1 from user_roles where user_id = _uid and role = _role)
$$;

create or replace function public.is_staff(_uid uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select has_role(_uid,'moderator') or has_role(_uid,'admin')
$$;
RLS rules (enable on every table):

Set the request user id with set local request.jwt.claims = ... or set local app.user_id = ... at the start of every transaction so RLS policies can read auth.uid() (define auth.uid() as a SQL function returning that GUC).

5. Authentication
Endpoints under /auth:

Method	Path	Body	Notes
POST	/signup	email, password, name	Argon2id hash; send verification email; create profile via trigger
POST	/login	email, password	Returns access JWT + sets refresh cookie
POST	/refresh	—	Rotates refresh token; revokes old one
POST	/logout	—	Revokes refresh token, clears cookie
POST	/verify-email	token	Marks email_verified_at
POST	/forgot-password	email	Issues reset token; always 200
POST	/reset-password	token, newPassword	Validates token, updates hash, revokes all refresh tokens
GET	/oauth/google	—	Redirect to Google
GET	/oauth/google/callback	code	Upserts user + oauth_accounts, issues tokens
GET	/me	—	Returns profile + roles
Requirements:

Argon2id, memoryCost ≥ 19 MiB, timeCost ≥ 2.
JWT signed with EdDSA (Ed25519) or RS256; keys rotated; kid in header.
Refresh tokens stored only as SHA-256 hash in DB.
Brute-force protection: per-IP and per-email rate limit on /login, /forgot-password, /signup (e.g. 5 / 15 min).
HIBP password check on signup and reset (k-anonymity API).
Email enumeration safe responses.
All tokens single-use, time-bound, and revocable.

14. Acceptance criteria
A new signup creates a users row, a profiles row, and a viewer role automatically.
A contributor can submit a place with images; it appears in /admin/submissions as pending.
A moderator can approve, reject, or request changes; approved places become public and contributions_count increments.
RLS prevents a contributor from reading another contributor's pending place (verified by test).
Admin can change a user's role from /admin/users and it takes effect on the next request.
Full-text search returns ranked results in < 200 ms for 1k places.
All endpoints return validated JSON with a consistent error envelope.
No runtime code references src/data/mock.ts.
